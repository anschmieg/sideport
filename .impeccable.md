# Sideport design guidance

## Design Context

### Users

The person at the Mac wants a remote agent to complete useful work while retaining local control. Technical users are the first alpha audience, but connection controls and consent must make sense without knowledge of MCP, JSON, sandbox profiles or tunnels. The interface should make access and activity easy to assess at a glance.

### Brand Personality

Calm, direct, accountable. Use the name **Sideport** and the descriptor **Computer use for remote agents.** Explain what will happen and give the user a clear choice. Avoid sales language, exaggerated security claims and product branding tied to a particular client.

### Aesthetic Direction

A small native macOS utility, using AppKit controls, system typography, semantic colors and standard materials. Respect light and dark appearance, contrast settings and reduced motion. The system microphone and screen-sharing pills are the reference for noticeable activity; Sideport's arrow/open-port glyph should remain distinct from a generic monitor icon.

Orange marks observed agent activity and desktop control. The status capsule uses the recording-indicator reference color and fills the status button without a second padded capsule. Off is neutral; availability alone must not look like an active session. Color needs a readable state label or accessible description. Keep the popover compact; avoid a dashboard, custom web-style toggle, ornamental gradients or a permanent overlay while idle.

### Design Principles

1. **Show actual state.** The switch represents the local access decision; the adjacent status explains progress, availability, activity or failure. An active pill reflects recent authenticated activity, not an exact live-agent count. Describe limitations in client attribution honestly.
2. **Make consent concrete.** Lead with the requested action, then why it is needed, what it permits and how long it lasts. Use specific button labels. A denial, dismissal or timeout must not imply approval. Technical detail is secondary and expandable.
3. **Keep local control reachable.** The desktop outline and client/Stop pill must be visible before input, readable, clickable and clear of the task's important controls. They must not take keyboard focus. Stop must communicate and perform disconnection.
4. **Avoid interruption without hiding risk.** Remember revocable folder choices and use configured command review for eligible cases. Do not stack prompts or repeatedly ask after failure. Escalations must remain noticeable and understandable.
5. **Use native interaction and accessibility.** Preserve keyboard navigation, VoiceOver names and state, sensible tab order, adequate contrast and layouts that tolerate long paths and client names. Do not rely on color, hover or animation as the only explanation.

## Applying this guidance

These are intended design constraints derived from the project discussion, not a claim that every current view passes an accessibility audit. For UI changes, review off, connecting, available, connected, failure and cancelled states as relevant. Review both appearances and long-content cases. Use synthetic native screenshots for documentation; validate live behavior separately through the controlled workflow in the development guide.
